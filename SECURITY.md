# Security

Do not put credentials, customer data, or exploit details in public issues.

For a vulnerability, use the repository's private security advisory channel if enabled, or a maintainer's published private contact. The repository owner must configure a reporting contact before public release. No response SLA is promised yet.

Besh starts as an early local-development project. A passing test suite is not a security certification. Before public deployment, require TLS, scoped identity, rate limits, encrypted secrets, isolated plugins, backup recovery checks, dependency review, and an independent security review.

See [architecture](docs/architecture.md) for trust boundaries and [AI policy](AI_POLICY.md) for agent access rules.

Selected API access is owner-managed and versioned, with existing members defaulting to all access. Eligible roles may use API read/write/test/publish, key management, and load testing, but no API creation or global resource administration. Every read/export seam applies current action/selection checks; inaccessible IDs return `404`. Accepted access updates revoke affected cookies with audit, and incompatible grant expansion fails before changes. Complete backups remain privileged whole-workspace snapshots. See [roles and sharing](docs/roles.md#selected-api-reading).

Selected actions require typed dependency USE across all graph branches, transaction boundaries, asynchronous data/provider checkpoints, and final results. USE can expose stored data through authored APIs; it is not row/column/tenant isolation. Structural catalogs exclude rows/counts, URLs, settings, and secrets. Selected issuance derives a current pin and issuer/action binding; calls require the original issuer’s current authority, and replacement preserves the binding even for an owner. Deleted issuers remain denied rather than becoming unbound; legacy null-bound keys retain unprotected behavior; live resource protection adds identity requirements. Scoped revoke/cancel remains available without USE while action/API scope permits it. These checks cannot undo effects already performed or instantly terminate admitted native work. See [selected actions and USE](docs/roles.md#selected-api-actions-and-dependency-use).

Only canonical backend modules regenerated from validated graphs may be loaded; uploaded or modified JavaScript is not trusted. Temporary module files and server filesystem access are privileged. Code downloads require API-read permission and may contain configured graph literals/resource references, though server-held credential values are not automatically inserted. Generation checks, current credential/pin checks, execution limits, and audit/data boundaries remain required. Failed peer reconstruction or local router restoration blocks runtime requests with `503` until restart or a successful local publication stage; this is not a distributed activation or availability guarantee. See [published backend code](docs/runtime-code.md).

Built-in k6 load testing requires `load-tests.run`, including target/history reads and cancellation. Owners have this permission by default; custom roles can receive it explicitly. Tests use the selected published API, validated request input, and an automatically issued temporary runtime key with only the required operation grant. Normal caller keys remain unchanged. Arbitrary URLs, uploaded scripts, shell commands, and custom request headers are not accepted. Product OAuth/social flows are unavailable for automatic testing.

Write methods and GraphQL mutations make repeated live requests. The dashboard requires confirmation; a permission-authorized API start authorizes these calls without an extra confirmation field. There is no rollback, and in-flight requests may finish after cancellation or key revocation. One active job, at most ten virtual users, at most thirty seconds of scheduled load, and a fixed pause bound this feature without isolating normal callers from resource use. Passing goals do not certify capacity or security.

First use downloads pinned official k6 2.3.0, verifies its archive SHA-256 against the release checksum, and caches the native executable. `BESH_K6_PATH` optionally executes an administrator-trusted existing binary; it is not a user upload or sandbox. Protect the cache and explicit binary path as executable server files. Run input and raw temporary tokens stay out of saved history, audits, and process logs; SQLite backups include endpoint/configuration/result metadata. Restart interrupts unfinished jobs and revokes their temporary keys rather than resuming work. See [load testing](docs/load-testing.md).

Owner and member credentials authenticate workspace management and authorized draft tests only. Published APIs require separate expiring runtime keys scoped to one published flow and REST, GraphQL query/mutation, or dedicated `ws` operations. WebSocket keys always pin the current release. Runtime keys cannot manage members, change flows, or test drafts. Issuing, replacing, and revoking keys requires `runtime-keys.manage`. The server stores token hashes, returns each token once, and checks expiration and revocation on every call.

Runtime-key handover is implemented in 0.14. Replacement preserves name, flow, grants, release pin or following mode, original issuer binding, tenant identity, and exact expiration. Optional strict integer `graceSeconds` ranges from 0 through 300 and defaults to immediate revocation. Positive grace records a fixed original-key cutoff; a requested deadline beyond its expiration is rejected, never clamped. New hash-only credentials, unique normalized predecessor/successor lineage, and metadata-only audits commit atomically. Migration 20 preserves fixed deadlines through restart/current-backup restoration without extending them.

Startup rejects missing or cross-scope lineage endpoints, cycles, and inconsistent schedule/successor creation stamps. Admission checks indexed adjacent descriptors without traversing the historical chain. These are consistency checks, not signatures or resistance to an owner restoring older security state.

Each key retains its own current authority and hard revocation boundary. At or after `acceptUntil`, or after explicit revocation, its credential is denied. At most two credentials remain eligible in a replacement chain: a key already replaced cannot be replaced again, and its successor cannot be replaced while the original approved window is live, even during temporary pin/issuer/tenant/field denial. Exact-key revocation never cascades. A lost response may mean replacement committed without delivery of its one-time token; inspect lineage and revoke the predecessor or await its deadline before replacing an eligible successor. Never automatically retry or replay the secret. See [runtime API keys](docs/api-keys.md).

Original WebSocket ticket/connection IDs and product OAuth `runtime:<keyId>` attempts never transfer to a successor. New WS tickets cannot outlive the original key's cutoff; earlier receipts also depend on the fresh original-key check. Frame/final/idle checks end expired sockets and cancel pending readers. OAuth rechecks the original credential after provider work and withholds identity after its window ends. Current final checks do not undo effects already admitted or recall queued/delivered bytes. Older database restoration can still restore older security state; this is not rollback-resistant external enforcement.

WebSocket browser tickets are hash-stored, origin-bound, single-use, and expire within 30 seconds. Draft tickets retain the exact original workspace session or native member-key proof; published tickets retain their runtime key. Every frame, idle sweep, asynchronous read, and final send checks current proof, revision/pin, issuer/action/API/USE, tenant, and admitted resource policy. Authority or policy loss closes the socket; shutdown cancels pending readers before stopping the listener. Connection/message/output bounds apply, but queued or delivered bytes cannot be recalled. No credential or nonce belongs in a WS URL. See [WebSocket APIs](docs/websockets.md).

Workspace email/password or member keys exchange into HttpOnly, SameSite=Strict browser sessions with a fixed 12-hour expiry. Passwords use Argon2id hashes; session secrets are stored as hashes. Cookie-authenticated writes require a session-bound CSRF token and the exact trusted browser origin. HTTPS cookies use Secure; HTTP is limited to loopback development. Configure the exact public origin for a reverse proxy. See [workspace authentication](docs/workspace-auth.md) for configuration, login limits, account changes, and revocation.

Account changes require a current password or that member's key and end other sessions. Owner-key recovery ends owner sessions when the key changes, while preserving the owner's password account. Restoring a backup may restore old passwords and unexpired sessions; review accounts and revoke restored access before serving the workspace. GitHub product login belongs to generated APIs, separate from workspace sign-in.

Operation grants do not provide field-level or record-level authorization. Following keys accept their flow across republishing, so broader published behavior also broadens what existing grants can invoke. Release-pinned keys accept only their exact graph revision while it is current, deny mismatches before typed inputs or effects, and never execute archived releases. An exact rollback can restore an unexpired, unrevoked pin; expiry/revocation still applies. Pins do not freeze mutable data/credentials or create tenant identity. Review following-key grants before publication. Restoring a backup can reactivate keys revoked or replaced since the snapshot and omit later replacements; review, revoke, or replace restored access before serving callers. Backup hashes cannot recover a lost raw token.

## Tenant rows — implemented in 0.11

Tenant-protected reads began in 0.11. Resource-owned policies narrow supported spreadsheet/SQLite API reads with exact owner-approved text identity, outside editable flow input. Every non-owner derives current assignment, including all-mode custom managers; protected credentials require a current pin and live issuer/action binding. Caller fields cannot assign identity. The 0.16 HTTP extension permits up to four protected reads and three input-only conditions, with every path reading data and one typed last-read reply. WebSockets retain their single-read scope. Joins, mixed protected/unprotected reads, social effects, product sessions and workspace isolation remain separate.

Mandatory exact tenant equality AND business predicates precede limits/projection. Source original TEXT is retained separately from normalized business values; legacy provenance needs reviewed reimport. SQLite explicitly uses BINARY comparison. Final failed authority/policy checks withhold protected REST/GraphQL/WS rows. Foreign tenant key/job metadata is hidden for every non-owner; original issuers retain scoped historical cleanup without minting authority.

The resource-global API field allowlist is implemented in 0.13. Owner-managed source/per-table policies gate configured returned columns and business-filter columns before tenant-protected reads, including owner-reviewed tests and existing pinned releases. The private tenant predicate may use an excluded column. All fields includes future columns; selected fields permits only explicit keys, may share none, and excludes new columns. Omitted fields persist, including while unprotected. An excluded field stops the whole read rather than silently redacting or rewriting graphs/schemas. Schema names remain structural metadata; raw owner previews and full backups keep their existing privilege. Migration 19 preserves these policies without changing compiler 2. See [API field allowlists](docs/row-protection.md#api-field-allowlists) and [testing](docs/testing.md) for acceptance status.

Tenant-specific field profiles are implemented in 0.15 for those canonical protected source/SQLite reads. The trusted current tenant chooses a sparse selected profile, or inherits current global fields when absent. Effective access always intersects the global allowlist. Configured projection and business-filter columns must wholly pass before rows are materialized or a native reader starts; asking for fewer GraphQL reply fields does not authorize a forbidden graph. Existing malformed stored profiles fail closed with `503`, distinct from missing inheritance. Private tenant predicates may still use excluded keys; raw owner data, backups, and structural schema-name access are unchanged.

Owner-only profile maintenance uses policy/resource/tenant review versions and atomic audits, including dormant resources or retired identities without activation. Profiles survive global policy changes, deprotection, and retirement. Bounded owner summaries identify configured tenants without full field maps or exact registry values. Source replacement/refresh checks every retained selection before mutation, including dormant and retired profiles; owner reset can recover replacement without activating either resource or identity. Save/publication/rollback keep the global gate; execution and caller authority apply the original trusted tenant's current profile. A profile edit advances the shared resource policy version, withholding pending results and closing affected sockets even for other tenants who remain allowed; fresh admission may restore their access. Migration 21 does not rewrite graphs or compiler-two artifacts. Tenant-profile delivery validation and bounded HTTP graph checks passed; product account authorization and multiple workspaces remain planned. See [tenant field profiles](docs/row-protection.md#tenant-field-profiles).

Member-specific ceilings are implemented in 0.17. Their current global/tenant/member intersection uses the authenticated draft member or original runtime-key issuer, never caller input or the member replacing a key. Owner-only updates review resource/policy/access/assignment/tenant/role values; deleted issuers deny before absent-profile inheritance. Non-owner replacement cannot deliver another issuer's bound key, while scoped historical revocation remains available. Complete local acceptance is tracked in [testing](docs/testing.md) and [member field profiles](docs/row-protection.md#member-field-profiles).

Field updates advance the same resource policy version and are checked again around asynchronous reads. Failed final checks withhold rows; affected WebSocket connections close and cancel pending readers. Restoring allowed fields can authorize the original graph/pin again, without a new publication. Closed sockets require a fresh connection. This cannot recall queued/delivered bytes or make backup restoration resistant to an owner restoring older security state.

Protected full/raw resource operations are owner-only. Asynchronous SQLite previews/checks recheck original management proof, current grant, and live raw-resource protection after child reads; a newly protected resource returns hidden `404` without rows/check metadata or a successful-check audit. Deletion and source/copy API generation repeat fresh proof/grant/raw-policy checks first after acquiring the IMMEDIATE write lock, before removing data, constructing templates/flows, or committing their audits. First protection permanently makes ordinary backup routes owner-only, including old archives after deprotection/restart. Streams recheck current actor/cookie/policy around bounded reads; interrupted archives can end normally and include bytes already delivered. Dashboard downloads reject incomplete blobs using reviewed byte metadata. Physical/manual older-database restoration can restore old security state and is outside this monotonic guarantee. See [row protection](docs/row-protection.md).

Unprotected spreadsheet previews require `sources.read`; import, replacement, refresh, and deletion require `sources.write`. Protected full/raw resource operations additionally require owner status. Review projected columns before generating a public-facing API. Published APIs read the latest saved snapshot; source replacement/refresh can change live data independently from graph publication. CSV/Excel imports and Google exports are bounded, uploaded code/formulas are not executed, and Google fetches restrict HTTPS hosts and redirects. Private Google OAuth and spreadsheet writes are not implemented. Backups contain imported rows and must be stored privately.

SQLite product connections are read-only uploaded copies. Unprotected connection metadata and previews require `database-connections.read`; upload, check, and deletion require `database-connections.manage`. Protected full/raw copy operations additionally require owner status. Draft generation also requires `flows.write`. For unprotected copies, all-mode draft tests and unbound runtime grants can execute configured reads without a separate database-read grant; selected operations and bound callers also check current issuer/API/USE authority, so review exposed columns and optional filters. For an unprotected resource, omitting an optional business filter returns unfiltered rows up to the configured limit. Protected resources always retain their mandatory tenant predicate. A filter is not field, record, or tenant authorization.

The trusted SQLite child program accepts inspected identifiers and bound scalar values, without caller SQL, external paths, extensions, or uploaded code. The private stdin frame carries a four-byte length, at most 16 KiB operation metadata, and at most 2 MiB SQLite bytes; neither database bytes nor tenant operation values are passed in process arguments. Each operation has a two-second deadline, 256 KiB output limit, and 16 MiB SQLite allocation budget; at most two readers run per Bun process. These limits do not cap whole-process memory or establish an OS sandbox. Uploads, tables, rows, text, and stored bytes have separate bounds. Drafts and every historical release protect referenced copies from deletion. See [database copies](docs/databases.md).

The complete original SQLite copy is stored unencrypted in the control database and included in workspace backups, even when an API projects only a few fields. Restrict database and backup access accordingly. The separate OAuth encryption key does not encrypt uploaded database contents. Restoring a backup restores these copies alongside flows and credentials; inspect restored access before serving callers.

Custom roles grant explicit actions without implicit grant expansion. Eligible API actions can be narrowed by separate sharing and typed USE; global resource, audit, and backup capabilities remain workspace-wide. Role/member administration and other-member session control remain owner-only. Current grants are resolved for every authenticated request; grant changes and member assignments revoke affected browser sessions with audit. Requests already authorized may finish. Draft testing can execute configured data and product-login steps; backup management permits downloading a complete sensitive workspace snapshot while backups remain delegable; first tenant protection makes ordinary backup operations owner-only. Review these permissions before assigning them. See [roles](docs/roles.md).

Update notices remain owner-only. Manual checks contact a fixed public GitHub API target, reject redirects, bound headers/body/time, and preserve a workspace cooldown across restart. Only safe release metadata is cached; provider response bodies are not logged. These notices do not download or apply updates, establish artifact authenticity, or verify compatibility. See [update notices](docs/updates.md).

GitHub product login requires a product server that holds the runtime key and separate login proof, associates each attempt with its initiating browser, and handles its own exact registered callback. Keep runtime keys and proofs out of browser code/storage, URLs, and logs. The template uses ten-minute, hash-stored state/proof, S256 PKCE, caller/flow/revision/connection-version binding, and one-use completion before bounded fixed-endpoint provider calls. It returns a verified provider identity without provider tokens or client secrets. It does not issue product sessions/JWTs, link email addresses, or enforce product record authorization. A passing controlled-provider test does not verify a real GitHub app or deployed callback. See [product login](docs/product-auth.md).

Provider client secrets and PKCE verifiers use AES-256-GCM encryption in SQLite with a separate local 32-byte key. The default `besh-secrets.key` sits beside the control database; `BESH_SECRET_KEY_PATH` can select another private location. This is encryption at rest, not an OS-keystore integration or certification. Restrict access to both the database and key: possession of both allows decryption.

SQLite backup downloads do not contain the encryption key. Back it up privately and separately, and restore the matching database and key together. Encrypted records with a missing key cause startup to fail rather than generate a replacement; losing the original key prevents recovery of provider credentials. SQLite backups still contain sensitive accounts, credential hashes, sessions, spreadsheet rows, and encrypted provider data. Connection edits affect live credential references and invalidate pending attempts even when published graphs stay immutable.
