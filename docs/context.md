## Choices and reasons

- Preserve built-in owner/editor/viewer grants and add custom roles through an explicit catalog rather than arbitrary strings or owner delegation. Member/role administration and other-member session control stay owner-only. Version-checked edits avoid lost updates; assigned roles cannot be deleted. Generate source drafts only with `sources.read` plus `flows.write`, and product-login drafts only with `auth-connections.read` plus `flows.write`.
- Describe sensitive grant effects directly: draft testing can execute configured data/social steps, key management can issue caller access, load testing can repeat live writes through managed temporary keys, and backup management can download complete sensitive workspace snapshots. These action permissions are not finer product-data authorization.
- Keep update checks owner-only instead of adding an arbitrary remote-fetch capability to custom roles. Canonical GitHub settings choose a fixed official release-list request; transport limits, a persistent cooldown/lease, and revision checks bound it. Discard pending responses after settings change. Compare eligible semantic versions among the first 20 releases; notice text cannot certify a downloaded artifact or authorize installation.

- One package and shallow folders kept the initial core easy to navigate. A large monorepo was unnecessary for that milestone.
- User prefers feature folders as the server grows. Authentication, spreadsheet data, database copies, flow execution, load tests, update notices, and workspace storage now live in seven named feature directories. Related lifecycle/policy code stays together; only application wiring, startup, and shared errors remain at `src/` root. Root runtime `/data/` and `/backups/` ignores keep private files out of Git while `src/data/` stays tracked. One package remains sufficient.
- SQLite makes the local wizard work without external services. Product database adapters stay distinct from control storage.
- Interpret validated graph JSON rather than executing generated code. Untrusted plugin runtime requires a later isolation design.
- Separate draft and published definitions to avoid changing live endpoints during edits. Revision checks prevent lost updates.
- Use role-scoped workspace accounts, sessions, and keys for management and separate expiring runtime keys for callers. Whole-query/mutation grants avoid conflating member access with published API execution. Separate resource policies protect canonical tenant rows and global/tenant fields, with member profiles in 0.17. GitHub product identity uses the runtime boundary; broader product authorization remains planned.
- Exchange workspace login credentials for fixed-lifetime HttpOnly cookie sessions so reload can restore sign-in without storing member keys or passwords in browser storage. Exact-origin and session-bound CSRF checks protect browser writes while explicit bearer management clients remain compatible. Keep account changes limited to the caller and require fresh credential proof; this avoids granting password changes from session possession alone.
- Retain owner-key filesystem recovery, but revoke owner sessions when that key changes. Preserve the owner's email/password account and document that it must be changed separately when compromised. Session revocation alone leaves passwords and member keys usable, and a restored backup can revive their earlier states.
- Use MIT for Besh with Besh's own copyright attribution.
- Use a bounded explicit schema subset rather than accepting arbitrary JSON Schema keywords. Convert declared numeric/boolean query text only; preserve exact JSON body/response types. Reject invalid input before execution and hide mismatched response data behind a generic 500.
- Generate OpenAPI 3.1.1 from the chosen saved REST snapshot. Omitted source means published, with no draft fallback. Emit schema/route/security metadata rather than inferring contracts from literals or leaking source rows and credentials. Old flows without rules remain compatible.
- Keep generated GitHub login as a normal request/social/response draft with `$auth`; REST uses POST with generated body/response rules and GraphQL uses a typed mutation. Generated Query.info is static to prevent a query grant from performing login. Generation neither publishes nor issues a runtime key.
- Require a product server to retain the runtime key, expected state, and separate sensitive proof associated with its initiating browser, and handle the registered callback. Do not make a public Besh callback or place runtime credentials in the browser/URL. The proof prevents state alone from completing an attempt; product browser association remains the product server's responsibility.
- Return normalized GitHub identity only. Product sessions/JWTs, account creation, email linking, and record authorization were left out of this slice rather than implied by provider identity. Limit network access to fixed GitHub endpoints and consume valid attempts before code exchange to prevent replay.
- Encrypt provider secrets and PKCE verifiers using a lazily created separate local key. Existing encrypted rows with a missing key fail startup rather than silently replacing it. SQLite backup downloads omit the key, so users must save it privately and restore the matching pair. Credential references stay mutable and connection-version changes invalidate attempts; published graph routes/rules remain immutable.
- Record product login start/consumption with their transient state changes and log completion/failure after provider exchange. Keep all attempt and provider secrets out of audit details. Generated REST OpenAPI includes the actual response rules and OAuth-specific capacity/provider errors.
- Complete the existing runtime credential lifecycle before adding another integration: replacement can be exercised through the authorized local HTTP and browser interfaces without external credentials. Reuse the runtime-key and audit tables rather than introducing a migration or a provider-dependent workflow.
- Replace keys in one transaction with `runtime-key.revoked` for the old ID and `runtime-key.created` for the new ID. Retain exact scope and expiration; reject settings in the replacement request. Check the current published protocol, not draft edits, so replacement cannot silently add grants or prolong lifetime. One concurrent replacement wins, and any transaction failure preserves the original.
- Choose immediate replacement with explicit confirmation and one-time copy/save. There is no built-in grace period: caller updates can have downtime, while gradual handover remains manual create/update/revoke. Check authentication at request entry, so already authenticated calls may finish. Avoid automatic replacement retries after response loss because a committed token cannot be fetched again; inspect metadata before recovery.
- Keep dashboard navigation and credential actions locked while a management request is pending. This prevents switching pages from discarding a successful replacement's one-time token before its response arrives. Besh home blocks navigation and browser unload warns while busy. After the response, leaving or reloading still clears the in-memory token as designed; save it first. Refreshing key metadata preserves an issued token.
- Keep product login attempts bound to their original runtime key ID. Replacement creates a new caller identity and cannot transfer pending OAuth attempts; start a new BEGIN attempt with the new key. An older SQLite restore can revive pre-replacement key state, so restored access needs review before service resumes.
- Reject every same-method overlapping REST route rather than adding literal-route precedence. This prevents an ambiguous URL from selecting a different flow under a scoped runtime key. Parameter names are safe, unique whole-segment identifiers; decoding happens once before validated execution. Version prefixes are explicit routes, not automatic compatibility promises.
- Reuse immutable release history for rollback. Require owner permission and the expected current publication, validate dependencies and route conflicts, and save the selected release with `flow.rolled-back` in one transaction. Preserve draft edits. References to current spreadsheet snapshots and OAuth connections are not historical data backups.
- Block publication and rollback of a flow while its load test is active. This prevents the tested route from changing during the run without claiming that mutable dependencies or repeated live writes are isolated.
- Configure CI validation and manual candidate artifacts with pinned tool/actions, version policy, and read-only repository permissions. Artifact inventories detect changed contents but do not establish signature authenticity. Hosted execution and authorized release publication remain separate from local configuration/checks.
